Качество данных

Сделайте качество частью выполнения, а не документом после него.

Data Quality преобразует ориентированные на источник требования в повторяемые SQL-проверки с ясным условием успеха, сохранённым QualityRun и ограниченными доказательствами ошибки.

Изучить процессы с контролем качества →

01

Начните с явного требования.

Визуальные шаблоны охватывают проверки NULL, пустых значений, уникальности, количества строк, диапазона значений, шаблона, допустимых значений и ссылочной целостности. Пользовательский SQL поддерживает более сложные проверки, если условие успеха определено точно.

01Проверки NULL и пустых значений

02Ограничения уникальности и количества строк

03Диапазоны числовых или сопоставимых значений

04Проверки шаблона SQL LIKE и допустимых значений

05Проверки существования ссылок

06Явные пользовательские SQL-проверки

02

Предварительный просмотр, сохранение и Run — разные действия.

Предварительный просмотр проверяет текущую интерпретацию. Сохранение создаёт или изменяет изменяемое правило. Немедленный запуск или поддерживаемый этап Pipeline создаёт постоянный QualityRun и ограниченный Finding при ошибке.

01Предварительный просмотр выполняется синхронно и не сохраняется.

02Сохранение изменяет определение изменяемого QualityRule.

03Немедленный запуск, Pipeline и выполнение Master сохраняют QualityRun.

04Ошибка сохраняет ограниченный Finding Data Quality; он отделён от процесса Assurance Finding.

03

Качество может управлять реализованным процессом.

Отдельное задание Data Quality или управляющий этап Master может остановить поддерживаемую последующую работу при ошибке. Точные PipelineRun, QualityRun и событие запуска остаются разными записями.

04

Минимальные привилегии остаются обязательными.

Для пользовательского SQL нет универсального независимого парсера одного оператора только для чтения. Модальное окно правила SQL Console также требует повторного запуска после редактирования SQL, поскольку прежний результат не подтверждает текущий черновик. Sources должны использовать учётные данные с минимально необходимыми правами чтения, а образцы ошибок не должны содержать секреты и ненужные персональные данные.

05

Текущие границы не скрываются.

QualityRule изменяем и не закреплён непосредственно за DatasetVersion. Выполнение наборов правил, автоматическое исправление, полный процесс устранения Findings и подтверждённая доставка уведомлений пока не поддерживаются. Управляемая таблица Sandbox участвует через System Sandbox Source своего Project, а не через отдельный скрытый путь качества.

Связанные темы

Операции с данными Подключайте, исследуйте, преобразуйте и выполняйте с явной областью и контекстом Run.

Переходите от разнородных Sources и контролируемых файлов к управляемым таблицам, проверкам качества и сохранённой истории выполнения, не сводя все коннекторы к одной модели запросов или записи.

→ Управляемые Datasets Превращайте определения данных в версионируемые активы с явным происхождением.

Dataset отделяет исследовательский SQL от многократно используемого контракта данных. Его стабильный идентификатор, неизменяемые версии и семантические метаданные создают контролируемую основу для отчётов, не скрывая происхождение источника.

→ Регуляторная и операционная отчётность Свяжите версии источников, решения о качестве, запуски отчётности и доказательства в одном контролируемом потоке.

Стройте отчётность на явных контрактах данных и результатах запусков, чтобы изменение показателя можно было проследить до доступного входа, версии, политики, выполнения и контекста расследования.
